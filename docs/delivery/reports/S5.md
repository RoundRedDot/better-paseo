需要父级知晓的两项缺口：

1. **iOS/Android 上偏好设置不会保留到 App 重启后。** 原因是 `preferences.ts` 用 `localStorage` 存储，而原生端没有 `localStorage`。这个问题从 v1 就存在，不是 S5 引入的。iOS 实测：设置当场生效，重启 App 后恢复默认。修复需要做一个决策：改用 SDK 的 `useSettings`（存在 daemon 端，所有客户端共享），还是等宿主提供按客户端存储的接口。这超出本切片范围，因此只在 README 中写明。
2. **打包体积与 iOS 冷启动基本不变。** 压缩后的 `marked.js` 文件小了 1.8 KB，但宿主的 esbuild 会把它重新排版输出，最终 bundle 里只省下约 1.6 KB。真正的大头是 `font-data.ts`（154 KB）和 `mark-bitmaps.ts`（137 KB），不在本次授权范围内。

## Findings（path:line — change）

### D3 的真实原因（与 V1 的推测不同）

- V1 推测是 `useAgent` 的 selector 每次返回新对象导致 memo 失效。实际上宿主的 `useAgent` 已经用 `useSyncExternalStoreWithSelector` 加 `shallowEqual` 比较选择结果（`paseo/packages/plugin/src/client/client-state.tsx`），所以 `{status, updatedAt}` 这个对象本身不会引起重渲染。
- 真正的问题是**订阅本身**：每张用户卡都订阅了 agent 的 `status` 和 `updatedAt`。agent 每更新一次，这个 agent 的所有用户卡都会重渲染；而且每张卡还会在 effect 里各发一次 `handle.refresh()` RPC。
- 证据：V1 的 dump（`raw-host-final/web-history-100-*.json`）中，每张卡的渲染次数随挂载顺序单调递减（102、92、92 … 7、5、3、2）。越早挂载的卡经历的 agent 更新越多，说明驱动它们的是 agent 级的信号，而不是卡片自己的数据。
- 其他 renderer 的 selector 都返回字符串（`usePathContextValue` 和 assistant 的 cwd），V1 数据中这些卡片也没有扇出（assistant 189、tool 165，与本次前后测量一致）。
