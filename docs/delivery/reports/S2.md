## Findings (path:line — change)

**D4: each closing fence shrank the card by 18 px.**
- Cause: inside an open fence, the closing fence arrives one character at a time. The repair skipped lines inside code, so `` ` `` and `` `` `` were drawn as a code row. When the third backtick closed the fence, that row disappeared: one row, 18 px, on every fence. It was not the header, the expand row or padding — open and closed blocks were otherwise identical.
- Fix: `client/components/markdown/repair.ts` `holdPartialFenceClose`. If the last line is a run of the open fence's character that is still shorter than the fence, it is held back. Fences are paired the CommonMark way (`openFence`), so a backtick run inside a `~~~` fence stays code.

**D5: flips on real hosts but 0 offline.** There were two causes.
1. **Real flips from the reveal skipping a held-back state.** A line `1` was a paragraph, the following `1.` was held back as empty, and `1. x` was a list. Offline, chunk by chunk, the empty step in between hid the change; on a real host, a reveal that jumps from `1` to `1. x` draws a paragraph turning into a list.
   - Evidence: a check that remembers each block's last visible kind found 14 such flips in markdown-long and 26 in history-100 (all `paragraph -> list` at `1.`). The markdown-long one at block 128 is exactly V1's web flip (`flipsByBlockIndex {"128": 1}`).
   - Fix: lines of digits alone are held back as well (`repair.ts` `LONE_MARKER_RE`).
2. **History-100 flips at blocks 0 and 1 were a probe artifact.**
   - Evidence: an instrumented web run (temporary, not committed; log in `s2-data/f1-web/fliplog-history-100-before-fix.json`) recorded 41 "flips". All 41 were between two *unrelated* replies sharing the probe id `assistant:<ms timestamp>`: 20 shared ids, 0 where one text is a prefix of the other, 0 within the same mount. At max speed several replies get the same millisecond timestamp.
   - Fix: `client/components/markdown/markdown-view.tsx` now counts each mounted view under its own serial (`instanceRef`, `mountSerial`).
   - Note for the host-side owner: the same timestamp is also part of the assistant renderer's `itemKey` (`useIsTimelineTail`). I did not change that, because it is outside the Markdown code.

### 2. Assistant `itemKey` collision

- `client/timeline-tail.ts`:
  - `textItemTailKey(kind, at, text)` = `kind:at:FNV-1a of the first 80 characters`, using the same hash and the same 80-character prefix as the reasoning key.
  - `renameTimelineItem(from, to)` moves the tail only when `from` holds it.
  - `useTextItemTailKey`: while a reply's opening is still under 80 characters, the key changes with each chunk. A passive effect then renames the tail entry; it runs after the child `TimelineTailHub` has noted the new key, which loses the tie to the old key at that point. So the tail follows the growing reply.
  - Once the opening is complete the key is fixed, and the history row that replaces the streamed row computes the same key.
- `client/live-renderers.tsx` (assistant section): `itemKey = useTextItemTailKey("assistant", ms, text)`. The flip probe keeps its timestamp id; it was already per mount.
- Remaining limit:
  - Two replies with the same millisecond **and** the same first 80 characters would still share a key.
  - For two same-millisecond replies, the tie rule ("ties keep the incumbent") gives the footer to whichever row was noted first. That is no longer two footers, but it can be the earlier reply. Fixing that properly needs a host item id.
