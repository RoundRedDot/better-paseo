状态：仅方案，尚未实施。各项先做前置验证，验证不成立即停止，不以完成全部条目为目标。

上一轮方案见 [2026-10-14 渲染、内存与加载速度优化方案](2026-10-14-performance-optimization.md)。其中 P1、P3 已交付；P2（Markdown 缓存预算）与 P4（高亮语法按需初始化）在前置验证阶段止损，证据见 [P2](../bench/2026-10-14-p2/README.md) 与 [P4](../bench/2026-10-14-p4/README.md)。本方案不重开这两项，除非出现新的证据。

## 1. 证据来源

2026-10-15 在 rrd-mac-studio（Apple M5 Max，18 核，64 GB）上做了四版本对比：不装插件（Paseo 0.11.2）、Beautiful Chat `42b61d8`、Better Paseo `9f270c6`（README 基线）、Better Paseo `37bfb60`（最新）。

| 平台 | 样本 | 原始数据 |
| --- | --- | --- |
| Web | 11 个回放 × 4 版本 × 3 次 = 132 | `docs/bench/native-vs-fork/raw/web-2026-10-15b/` |
| iOS 18.6 模拟器 | 一般场景每版本 2 次，`history-100`、`shell-log-large` 每版本 6 次，共 120 | `docs/bench/native-vs-fork/raw/ios-2026-10-15b/` |

原始数据随 README 性能更新一并提交；提交前位于 `.worktrees/bench-ba`。

证据边界：

- iOS 的 `history-100` 后三轮与其他场景的第 2 轮跑在三台模拟器并行的阶段。并行使 `history-100` 四个版本的行渲染总量都上浮约 3%（版本间同向），绝对值偏高。
- 同一份基线代码 `9f270c6` 在两轮 Web 测量之间，`history-100` 的 Task 中位数从 0.823 s 变到 0.761 s（约 7.5%）。本轮没有同轮 A/A 配对，10% 附近的差异不能单独定性。
- iOS 一般场景每版本只有 2 次，任何不足 15% 的差异都只记录、不判定。
- 本方案中 `37bfb60` 之后合入的改动（信息栏详情表、提示、样式等）未经测量。

### M0：测量口径补齐

1. **同轮 A/A**：每轮测量对每个关注场景至少做 3 对基线对基线交替运行，按上一轮方案 §2 的 A/A 规则报告最大配对差。O1～O5 的判定阈值只取本轮 A/A，不用历史数字。
2. **iOS 样本量**：关注场景每版本至少 5 次，按版本轮换顺序；`history-100` 必须单模拟器串行。
3. **并行环境的使用边界**：多模拟器并行只用于功能验收和粗筛。凡写入 README 或作为交付判定的绝对值，一律单环境串行测量。
4. **多环境工具固化**：把本轮验证过的步骤整理进 `docs/bench/` 的工具说明：
   - 新模拟器关机时合并通知授权项；
   - 用 `--initialUrl` 免提示启动；
   - 通过 Metro CDP 在 app 内导航，Hermes 中用 `.then` 加完成标记轮询，不用 `async`；
   - 每个新单元开始前检查 1 分钟负载不超过 4。
5. **探针**：在 `/bc-perf` 下为信息栏补计数：
   - 信息栏挂载与重渲染次数；
   - `createTurnFooterStore` 的 `read` 次数和翻页次数；
   - `needsOlder` 的比较次数；
   - `publish` 次数。

   探针关闭时不做额外工作。

### O1：长历史下每轮信息栏的成本

**现象**（Web，中位数，各 3 次）

| 指标 | 不装插件 | 基线 `9f270c6` | 最新 `37bfb60` |
| --- | ---: | ---: | ---: |
| Task (s) | 0.745 | 0.761 | 0.854 |
| Script (s) | 0.617 | 0.638 | 0.716 |
| 行渲染总量 (ms) | 155.7 | 170.3 | 218.9 |
| 提交次数 | 126 | 133 | 151 |
| 每次提交 p95 (ms) | 5.50 | 3.80 | 5.80 |
| 长任务总时长 (ms) | 55 | 59 | 0 |

- 上午一轮（最新为 `7182232`）基线与最新持平：Task 0.823 s 对 0.804 s，行渲染 191.3 ms 对 177.9 ms。
- `mixed-turn` 同方向：Web 每次提交 p95 从 2.5 ms 到 3.2 ms；iOS 行渲染总量从 220.2 ms 到 247.2 ms（+12%）。
- iOS `history-100` 基线到最新 +4%，在并行污染和样本量之内，不判定。

**已排除**：`history-100` 夹具只有 Bash 90、Read 84、Edit 84、Grep 72 个工具调用，没有图片，所以图片分帧交付（`34d7785`）不能解释这项差异。

**嫌疑**：`7182232..37bfb60` 之间，客户端最大的新增是每轮回复的信息栏：

- `1fd2d5b`、`187c072`、`d626bf6`；
- 新增 `client/state/turn-footers.ts`、`turn-duration.ts`、`footer-model.ts`；
- `history-100` 有 100 个已完成轮次，每轮一个信息栏。

源码中可能的成本来源（未测量，待 M0 探针确认）：

- [turn-footers.ts](../../client/state/turn-footers.ts) 的 `retain` 每挂载一个信息栏就调用一次 `needsOlder(entries)`。后者对每个目标做一次 `findIndex` 全表扫描，挂载 n 个信息栏的总比较量随 n² 乘条目数增长。
- 新轮次开始或结束时，`refresh` 会从尾部重新分页读取整条时间线，每页 200 条，直到覆盖最早的目标。历史越长，每轮结束时的 RPC 和解析越多。
- 信息栏的数据在读取完成后才到达：每个信息栏先渲染空，再渲染内容，提交次数随之增加。这与提交次数从 133 增加到 151 的方向一致，尚未对应到具体提交。
- [live-renderers.tsx](../../client/live-renderers.tsx) 中每个 `CompletedReplyFooter` 各自订阅 4 个 `useAgent` 选择器，并调用一次 `useFooterModel`。
- `37bfb60` 之后信息栏又加了详情表、提示和样式（`c540e18`、`0327acb`、`ede2a88`），当前成本未知。

**前置验证**

1. 在当前 main 上用 M0 探针跑 `history-100`，记录上面四项计数，以及 React Profiler 中信息栏子树的提交次数和渲染时长。
2. 对照实验：关闭信息栏（在测量构建中让 `useTurnFooter` 恒返回 null，只用于测量，不交付）。如果 Task、行渲染、提交次数回到基线的 A/A 范围内，归因成立；否则本项停止，另找原因，按 `7182232..37bfb60` 逐个提交二分。

**候选改动**（归因成立后选做，逐项测量）

- `needsOlder` 改为对条目建一次索引（`at`+`text` 到下标），把逐目标的全表扫描降为查表；`retain` 期间合并为每个微任务只检查一次。
- `refresh` 只读取新增的尾部条目，与已有 `entries` 拼接；只有 `replacement`、`subscription_restored` 才整条重读。
- 信息栏数据在同一次提交中批量到达：读取完成后一次 `publish`，避免逐个信息栏先空后满。
- 把 4 个 `useAgent` 选择器合并为一次订阅，或在时间线层级读一次后向下传。

**不做**：不隐藏信息栏，不延迟显示，不改变历史轮次的耗时口径和显示内容。

**验收**

- 功能：信息栏内容、耗时、复制、详情表、运行中保留已完成信息栏，与当前一致；单测覆盖分页、重置、轮次取消与失败。
- 性能：Web `history-100` 的 Task、行渲染总量与提交次数，相对「关闭信息栏」对照的差值不超过本轮 A/A 最大配对差；`mixed-turn` 不回退。iOS 在串行条件下复测，不回退。

### O2：展开的工具行流式输出（iOS）

**现象**（iOS，中位数，各 2 次）：

| 指标 | 不装插件 | 原插件 | 基线 | 最新 |
| --- | ---: | ---: | ---: | ---: |
| 行渲染总量 (ms) | 165.8 | 3,032.6 | 251.9 | 256.6 |
| 单行 p95 (ms) | 4.65 | 55.73 | 3.59 | 3.55 |

Web 上最新版 Task 比不装插件低 24%（1.577 s 对 2.062 s），但行渲染总量高 81%（109.1 ms 对 60.3 ms），单行 p95 高 33%。单行 p95 不差，说明是渲染次数多，而不是单次慢。

**前置验证**：用 M0 的样本量串行复测，并拆出该场景的提交次数、每次提交的行数、工具行组件的渲染次数。对照回复和预览已采用的分块重绘（`768ff43`、`27e5e81`），确认展开的工具输出是否每来一块就整体重渲染。

**候选改动**：只有在确认「每块整体重绘」后，才把同样的分块复用应用到展开的工具输出：已稳定的行保持引用不变，只重绘尾部。不改变折叠阈值、显示全部、换行和复制。

**验收**：iOS 行渲染总量相对基线的下降超出本轮 A/A；输出、行号、折叠和复制与基线逐字一致。

### O3：思考流式（iOS）

**现象**（iOS，行渲染总量，中位数）：

| 场景 | 不装插件 | 基线 | 最新 |
| --- | ---: | ---: | ---: |
| `reasoning-long-prose` | 262.4 ms | 314.6 ms | 321.3 ms |
| `reasoning-long-sections` | 244.5 ms | 270.3 ms | 283.5 ms |

Web 上同场景的行渲染总量远低于不装插件（154.0 ms 对 550.5 ms），差距只在 iOS 出现，可能与原生文本组件的重排成本有关，尚未核实。

**前置验证**：串行复测，统计思考卡片在流式期间的渲染次数，以及实时标题预览的更新频率；确认回复的分块复用是否已覆盖思考正文。

**候选改动**：在验证确认重复重绘后，让思考正文复用回复的分块重绘；实时标题预览只在标题变化时更新。不降低流式刷新频率，不改变分段规则和默认折叠。

**验收**：iOS 行渲染总量下降超出 A/A；分段、标题、耗时显示不变。

### O4：读取行（低优先级，只做归因）

- iOS `reads-20` 行渲染总量：不装插件 276.1 ms，最新 305.8 ms（+11%）。
- Web DOM 节点：最新 2,111，不装插件 1,885（+12%）。Task 最新低 12%。

先统计每个读取行的 DOM 节点和组件构成（路径、图标、悬停处理），列出比宿主多出的部分及其功能。没有冗余就停止；不为减节点删除功能。

### O5：iOS 大 diff 与长终端输出相对基线上浮

| 场景 | 基线 | 最新 | 样本 |
| --- | ---: | ---: | --- |
| `diff-large` 行渲染总量 | 33.2 ms | 46.2 ms | 每版本 2 次 |
| `shell-log-large` 行渲染总量 | 34.1 ms | 45.1 ms | 每版本 6 次，部分并行 |

Web 上同场景两版持平（21.0 ms 对 18.3 ms；19.5 ms 对 19.5 ms）。

先在单模拟器上每版本串行 5 次，并做 A/A。确认后再在 `9f270c6..37bfb60` 中按提交二分。首先怀疑横向滚动宽度的提交时机改动 `633d208`，以及信息栏（O1）。确认不了就停止。

### O6：插件常驻内存与包体（只测量）

- Web GC 后 JS 堆：最新比不装插件多 2.2～5.8 MB 的场景有 8 个，表格流式多 0.7 MB；代码块流式少 1.95 MB，长 Markdown 少 41.1 MB。相对基线多 0.1～2.3 MB，都在 10% 以内。
- 客户端包：`node .showcase/tools/bundle-size.mjs` 在 `0327acb` 为 943,311 bytes（gzip 216,925）。上一轮方案记录的 `b22fd52` 为 811,607 bytes（gzip 187,866），增长约 16%。插件包在每次重连时都会重新下发并解密，体积直接影响重连耗时。

本项只做两件事：

1. 测一次空会话的插件常驻堆，按模块归因，例如高亮客户端缓存、Markdown 缓存、字体与品牌图片。
2. 测一次重连时的包传输与求值耗时。

没有明确的冗余，就不改。

## 3. 暂不实施的方向

- 不重开 P2、P4，理由见各自的止损记录。
- 不在插件内做时间线虚拟化，不降低流式刷新频率，不以减少显示内容换取性能。
- 不为降低包体拆分设置页、删除语言或品牌资源，除非 O6 测出明确的冷启动或重连瓶颈。
