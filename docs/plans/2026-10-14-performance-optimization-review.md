## 有证据的问题

**Major**

1. **§5 验收规则无法让 P1 通过，也会被噪声误触发。** 方案第 174 行要求"目标指标收益应超过配对基线的波动"，第 85 行又要求同时报告宿主耗时差异。P1 省掉的是每次重渲染一次 FNV 全文遍历 `client/highlight.ts:206` 和一次 map 加 spread `client/components/syntax-highlight.tsx:685`，量级是微秒到低毫秒。而 `docs/bench/native-vs-fork/README.md:186` 和 `:199` 记录的同场景配对噪声在 10% 到 17%，整段主线程时间看不出这种收益。"非目标指标恶化超过 5% 就复测"也会在这种噪声下反复触发。建议：P1 的主验收改为确定性计数，例如在 hook 内加 perfCount 统计 cacheKey 调用次数或哈希字节数，用单测断言内容不变的重渲染不再计算；宿主耗时只做非回退检查，阈值按实测配对波动设定，或要求至少 5 对。

2. **P2 "单个超大条目可以不进入缓存"会制造回退。** `client/components/markdown/render/md-block.tsx:35` 在每次 MdBlock 渲染时调用 lexBlock，memo 只挡住 raw、open、context 不变的渲染。主题、字号、variant 切换会换 context，流式结束时 open 翻转，这两类场景都会重新渲染已完成的块。今天超大块命中 `client/components/markdown/lex.ts:84` 的 LRU，改成不入缓存后，每次主题或字号切换都要重新 lex 这个最大的块，而这正是 §5 矩阵里"深浅主题、字号和字体切换"要守住的场景。建议：超预算时仍至少保留最近使用的若干条或当前可见的条目，不允许任何条目被完全拒绝入缓存；并把"大代码块加主题切换"列为 P2 的必测用例。

3. **P4 缺少 Shiki 语法依赖的具体事实，按现稿实施会出错或产生顺序依赖的输出。** 已核实 `node_modules/@shikijs/langs/dist` 4.4.3 的三点：
   - html 的 `embeddedLangs` 是 javascript 和 css。`@shikijs/primitive/dist/index.mjs:305-316` 的 loadLanguages 在缺少依赖时直接抛 "Missing languages"。按需加载 html 必须连带加载这两个。
   - markdown 的 `embeddedLangsLazy` 覆盖了 18 种中的 15 种。`index.mjs:273-298` 显示，之后每加载一种被它懒嵌入的语言，markdown 语法会被删除并重建。于是同一段带围栏的 markdown，在 typescript 加载前后高亮结果不同。客户端缓存 `client/highlight.ts:49` 和服务端缓存 `index.server.ts:420` 会把"较少高亮"的早期结果永久保留。这打破了方案第 139 行的"输出等价"。建议：要么把 markdown 和它在支持集合内的懒嵌入语法作为一组加载，要么在等价性测试里明确加入"新引擎先高亮含围栏的 markdown，再加载其他语言"的用例并接受结果。
   - 当前 `index.server.ts:340-348` 的 fromHint 依赖 `getLoadedLanguages()` 返回的别名集合。语法文件自带的别名有 ts/cts/mts、js/cjs/mjs、bash/sh/shell/zsh、py、yml、md、rs、ps/ps1/pwsh。其中 cts、mts、cjs、mjs、ps、pwsh 只靠语法别名工作，不在 ALIASES 表里。显式映射必须复制这些。可操作的验收是：用急加载引擎导出一份 getLoadedLanguages 快照作为 fixture，断言懒加载映射与之相等。

**Minor**

4. **P1 顺带修复一个潜在崩溃，方案应把它写成行为修复并加测试。** `syntax-highlight.tsx:685` 用 spread 调用 Math.max，参数个数受引擎上限约束。`diff-lines.ts:12` 对整个 diff 生成 numbers，`LARGE_BLOCK_LINES` 只限制挂载行数，不限制这个数组。超长 diff 在客户端可能抛 RangeError。Hermes 的具体阈值未核实。

5. **P1 的单测没有现成可复用的 mock。** 没有测试直接导入 `client/highlight.ts`。现有 mock 都是 `useRpc: () => () => Promise.resolve(null)`，`highlight.ts:138` 的 readResponse 会把 null 判为无答案，缓存命中路径从未被覆盖。新测试需要按 `shared/highlight-rpc.ts` 的 output 形状返回 lines 和 language。

6. **P3 的连接身份有确定事实，方案可以直接写明而不是留待核对。** 宿主 paseo `759532509`，即 v0.11.2，`packages/app/src/plugins/registry.ts:68-105` 对每个 `serverId/pluginId` 单独 eval 一次客户端 bundle，并绑定该 server 的 invoke。因此插件的模块级状态在这个宿主版本里本来就是按 daemon 隔离的。另外 `@getpaseo/plugin/dist/client/rpc-context.js:13-18` 显示 useRpc 返回的是每个组件实例各自的 useCallback，load 函数身份不能当去重键；usePluginRpcContextValue 也未从 `@getpaseo/plugin/client` 公开导出。可行做法是模块级 Map 以 cwd 加 path 为键，并在代码注释里记录对"每安装一次求值"的依赖。`paseo-plugin.json` 声明兼容 `>=0.8.0`，旧宿主是否同样隔离未核实。

7. **P3 收益预期偏低，应排在 P0 数据之后。** 调用方只有 `client/live-renderers.tsx:182`，仅在展开或预览后请求，和 `client/components/markdown/render/local-image.tsx:11`。同一路径同时在途的情形依赖 agent 重复读同一张图并同时展开。P0 的"RPC 次数"目前也只统计高亮，见 `client/debug/store.ts:111`，没有图片 RPC 计数，需要先补探针才能证明有重复请求。

8. **P2 应引用已有的测量工具和数据，并写明止损规则。** `docs/bench/tools/recheck-lex-retention.ts` 已经按 fixture 重放并输出 GC 后的保留量。`docs/bench/2026-10-12-regression-recheck.md:45-48` 显示四个重 fixture 跑完后的保留量在 0.82 MB 到 1.65 MB。预算机制的收益上限就在这个量级，除非 history-100 类会话把 500 槽填满大块。建议在 P2 写明：先用该工具跑 history-100 和 markdown-long，若 500 槽满时保留量低于某个阈值就停止 P2。

9. **P0 的"daemon 内存"没有探针。** `server/perf-dump.ts` 不含 memoryUsage。P4 的实施前验证需要在隔离 daemon 里读 `process.memoryUsage()`，这应写进 P0 或 P4 的准备步骤。

**Nit**

10. 方案第 141 行"动态 import 只延迟执行"与 `index.server.ts:261` 的注释一致，但 P4 还应说明懒加载会把一次首次高亮延迟拆成每种语言各一次，会话内出现更多次"先无色后上色"。
