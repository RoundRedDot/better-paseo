## 1. 目标与原则

在保持当前功能、视觉和交互语义的前提下，减少重复计算、可重建缓存的保留量与重复资源请求，改善首次高亮体验。

- 最小改动，逐项实施、测量和回滚，不同时更换解析器或渲染架构。
- 不引入新依赖，不修改公共 RPC 契约，不增加新的降级路径。
- 不通过减少内容、降低高亮质量、改变默认折叠行为或延迟流式显示换取性能。
- 性能提升必须有同条件前后对照。各阶段按 §5 的阶段证据规则判定：以确定性证据为主的阶段，须同时满足确定性证据成立和宿主指标不回退；以测量为主的阶段，收益须超出当前 A/A 配对差异。功能回归或结果不确定时，不进入交付。
- 无法预先保证绝对零 Bug；以行为等价测试、宿主验收和独立回滚控制风险。

### P0：建立可比较的基线

沿用现有回放 fixture、宿主探针和生产构建方法，先确认脚本实际指向的 daemon、宿主及插件 revision，不直接操作日常使用的实例。

记录：插件和宿主 SHA、构建模式、平台、设置、fixture、回放速度、机器负载、冷/热状态、采样口径。基线与候选交替执行，至少 3 次配对，报告中位数与范围；波动较大时补到至少 5 次。

需要补充的场景：

- 大代码或 diff 内容不变，连续展开、换行及切换主题。
- 多个大 Markdown 块、长流式尾块、多个回复同时流式输出。
- 同一路径图片在多个组件同时出现；不同连接有相同路径。
- 第一次高亮与后续高亮分开测量，包括纯文本及混合语言。
- 多轮打开、关闭会话后测量内存，区分稳定缓存与持续增长。

记录主线程 CPU、React 提交耗时 p95、长任务、布局偏移、RPC 次数及响应体积；内存分别记录 GC 后 JS 堆、DOM 节点、daemon 内存，图片场景另看解码资源占用。不得将这些指标混为一个“内存”数字。

**当前 A/A 配对差异**：每个场景先做至少 3 对基线对基线（A/A）交替运行。每一对记录同一指标、同一单位的两次读数之差，耗时类同时记绝对差（毫秒或秒）和相对差（百分比），内存类记绝对差（MB）和相对差。报告每对的差值、所有对里绝对值最大的差，以及重复次数。这组数值是 §5 判定规则里“当前 A/A 配对差异”的唯一来源；历史基准文档中的波动数字不得代入。3 对之间差值方向或量级明显不一致时补到 5 对；仍不一致则该指标只报告、不判定。

**图片 RPC 探针**（P3 的前置）：`client/debug/store.ts` 目前只统计高亮 RPC（`highlightRpc`，第 111 行），没有图片 RPC 计数。P0 在调试探针内补一项图片 RPC 计数，并记录“同一 `cwd` 加 `path` 在途期间再次发起”的重复次数。探针只在 `/bc-perf` 打开时工作，不改变请求行为。P3 以这项重复次数为去留依据。

**daemon 内存测量方法**（P4 的前置，P0 建立口径）：

- 隔离范围：只在独立的 daemon 实例上测（与宿主基准相同的做法，例如单独的 Paseo 主目录和私有端口），不读日常实例。引擎初始化成本另用离线 Node 脚本直接加载 `index.server.ts` 的 handler 复测一遍，排除宿主其他负载。
- 读数：`process.memoryUsage()` 的 `rss`、`heapUsed`、`external`、`arrayBuffers` 四项分别记录。这些都是整个 daemon 进程的读数，不对应某个对象或某个插件。`heapUsed` 只能通过同一进程内“操作前后的差值”或配合堆快照归因到语法与主题对象；`arrayBuffers` 已包含在 `external` 内，二者不得相加；`rss` 含分配器碎片。四项各自报告，不合成一个数字。
- 采样时机：插件加载后空闲、第一次高亮请求完成后、覆盖全部 18 种语法各至少一次后、以及每个采样点在可用时先强制 GC 再读。每个时机至少 3 次冷启动取中位数与范围。
- 读数通道：P0 期间只允许通过调试用途的 `perfDumpRpc` 或离线脚本输出，不新增面向用户的 RPC。

### P1：减少确定的重复计算

**源码依据**

- [client/highlight.ts](../../client/highlight.ts) 第 206 行：`useHighlightedLines` 每次渲染调用 `cacheKey`，对 `code` 和可选 `diffBodyCode` 计算全文哈希。
- [client/components/syntax-highlight.tsx](../../client/components/syntax-highlight.tsx) 第 685 行：`SyntaxHighlightBlock` 每次渲染通过 `numbers.map` 和 spread 调用 `Math.max` 重新计算行号最大值。`numbers` 由 [diff-lines.ts](../../client/components/diff-lines.ts) 对整个 diff 生成，`LARGE_BLOCK_LINES` 只限制挂载行数，不限制这个数组的长度。

单次省下的工作量尚未在当前宿主上测量；本阶段不预设收益数字。

**计划改动**

1. 在 hook 内按 `code`、`language`、`filename`、`dark`、`diffBodyCode` 缓存键计算；保持现有键格式和请求行为。
2. 按 `numbers` 缓存最大行号，使用一次遍历避免中间数组和 spread 调用；无行号数组时继续使用原有 `total` 逻辑。
3. 保留流式期间 `enabled: false` 时的缓存读取语义，不能直接跳过全部逻辑。
4. 在调试探针下为“键计算次数”和“最大行号计算次数”各加一个计数（沿用 `perfCount`），作为本阶段的主证据来源。探针关闭时不执行计数，也不做额外遍历，只保留 `perfOn()` 这一个条件分支。

**待复现风险：超长 diff 的 spread 调用**。以 spread 传参的 `Math.max` 受引擎参数个数上限约束，diff 行数不受客户端限制，因此理论上存在 RangeError 的可能。目前没有任何平台的实际失败证据，不作为已证实的崩溃处理。处理方式：改动 2 落地时同时加入超长 diff 用例（行数远超 `LARGE_BLOCK_LINES`，例如数十万行的 `numbers`），在 vitest 中断言不抛错且最大行号正确；并按现有的平台验证流程（iOS 模拟器、Android 平台）打开一次同规模 diff 做人工确认。本方案不新增真机连接作为前置条件；未获授权的平台标记为未验证。`npm run check:hermes` 只在加载时求值，不覆盖这条渲染路径，不能替代该确认。

**预计文件范围**

- `client/highlight.ts`
- `client/components/syntax-highlight.tsx`
- 新增针对高亮 hook 的单测，以及补充代码行号/渲染测试。

**测试要求**。目前没有测试直接导入 `client/highlight.ts`；现有 mock 一律是 `useRpc: () => () => Promise.resolve(null)`，而 `readResponse` 会把 null 判为无答案，缓存命中路径从未被覆盖。新测试必须用真实有效的回包 mock，按 [shared/highlight-rpc.ts](../../shared/highlight-rpc.ts) 的 output 形状返回 `lines`、`language`、`theme`，并至少覆盖：

- 命中：同一请求第二次挂载不再调用 RPC，渲染期即可读到结果。
- 去重：两个实例同时挂载只发出一次调用，两者都收到结果。
- 失败：RPC reject 后记为 null，不重试，组件走本地着色。
- 纯文本提示：`language: null` 回包在 plain 提示下被接受，其他情况被拒绝。
- `enabled: false`：只读缓存，不发请求。
- 键维度：同长度不同内容、主题、语言、文件名、diff 正文各自变化都不命中旧结果。
- 卸载：结果在卸载后到达不触发状态更新。
- 重渲染：props 不变的重渲染，键计算计数不增加；任一维度变化后计数加一。

**验收**

- 主证据：上述计数在“内容不变的重渲染”用例中为零增量，在“内容变化”用例中按预期增加；行号、宽度、复制内容和最终高亮输出与基线一致。
- 行为等价：空内容、流式到完成、并发挂载、RPC 失败和卸载后的行为不变。
- 宿主性能只做非回退检查：相关场景（§5 矩阵中“大 diff”和“主题、字号切换”）的候选对基线差，不得超过 P0 同场景同指标的 A/A 配对差异中绝对值最大的一对。不要求在宿主耗时上看到可感知收益，也不以此宣称加速。

### P2：为可重建 Markdown 缓存增加容量预算

**源码依据**

[client/components/markdown/lex.ts](../../client/components/markdown/lex.ts) 第 65 至 110 行按条数限制完成块为 500、流式尾块为 8；单个条目的源文和 token 树大小不固定。客户端与服务端高亮缓存也各按 200 条限制。

[md-block.tsx](../../client/components/markdown/render/md-block.tsx) 第 35 行在每次 `MdBlock` 渲染时调用 `lexBlock`；memo 只挡住 `raw`、`open`、`first`、`context`、`id` 都不变的渲染。主题、字号、variant 切换会换 `context`，流式结束时 `open` 翻转，这两类场景都会让已完成的块重新渲染并再次查缓存。因此，任何让大块落出缓存的策略，都会把大块的重新解析搬到主题、字号切换和流式收尾上。当前实现里尾块转完成块本来就会在 LRU 未命中时重新解析一次，这一次不归因于本阶段。

**首批范围仅限 Markdown 解析缓存**：保留现有条数上限，同时增加可解释的权重预算。权重用源文长度作代理，比例系数由采样决定；估算权重不得称为精确字节数。禁止在热路径使用 `JSON.stringify` 整棵 token 树测大小。

**超大块与预算的折中**。不能简单把超大块拒之门外，也不能无条件保留所有超大块。下面两种设计只是待测候选，实施前必须用前置测量在两者之间选定一种，或两者都放弃：

- A：超大块照常入缓存并计入预算，淘汰从最老条目开始，但最近插入的一条不淘汰。
- B：超大块进入独立的小容量槽位（按条数限制，例如 1 到 2 条），主缓存预算不受其影响。

两种候选都不保证多个可见大块在主题切换时全部命中：三个大块 A、B、C 依次渲染后切换主题，它们会按序互相淘汰并抖动重解析。因此不写“当前渲染的块总能命中”之类的保证，也不以零未命中作为验收。两种候选的保留量上界都是“预算加若干个最大输入条目”，而单个输入条目的大小不受本方案限制，所以这不是固定字节的硬上限；单条无限制时没有固定内存上界，这一点要在实施记录里写明。共同约束只有：超预算只淘汰缓存，后续仍用同一解析器重新计算，不省略渲染内容，不影响调用返回结果；完成块与流式尾块继续分开管理。

前置测量必须包含“多个超大块同时可见，来回切换主题与字号”的用例，记录两种候选相对当前实现的未命中次数和重解析耗时。若没有一种候选能在不增加这类场景重解析的前提下降低实测保留量，本阶段停止；不扩大范围去实现可见块固定（pin）或其他新机制。

**前置测量与止损流程**：

1. 用现有的 [recheck-lex-retention.ts](../../docs/bench/tools/recheck-lex-retention.ts) 离线重放 `history-100`、`markdown-long` 与一段模拟多会话浏览的序列，记录 LRU 条目数与 GC 后保留量。该工具在 [2026-10-12 的复测](../bench/2026-10-12-regression-recheck.md) 中跑过四个 fixture，当时的数值只说明那几个 fixture 的离线保留量，不是通用收益上限，也不是宿主内存结论。
2. 在调试探针下加一个“完成块缓存未命中”计数，在 P0 的“主题、字号切换”和“100 轮历史”场景里记录当前实现的未命中次数，作为对照。
3. 止损判定分两个口径，不互相代入：
   - 离线口径：在同一 Node 运行时里，先对当前实现重复运行该工具至少 3 次得到离线 A/A 差异，再对候选实现运行同样的序列。候选的保留量降低必须大于离线 A/A 差异中绝对值最大的一对，否则本阶段停止，不写宿主代码。
   - 宿主口径：候选进入宿主后，GC 后 JS 总堆的候选对基线差与 P0 同场景的宿主 A/A 配对差异比较。差值未超出 A/A 差异时，只能记为“宿主上未观察到”，不能据此宣称收益，也不能据此宣称不可能观察到。
   本文不预设任何 MB 阈值。
4. 通过离线止损后，按采样结果定预算与系数，选定 A 或 B，再进入实施；宿主口径在实施后作为交付判定的一部分。

**预计文件范围**：`client/components/markdown/lex.ts` 及 Markdown 缓存相关单测；仅在两个缓存确实需要共享逻辑时添加小型内部模块。

**验收**：淘汰前后 token 输出一致；覆盖脚注、引用定义、HTML、表格、未闭合围栏、并发流式与重挂载；超预算条目不长期占用缓存；必测“单个大块”和“多个大块同时可见”各自加主题切换、字号切换、流式收尾的用例，报告候选与当前实现的未命中次数对比，多个大块场景的未命中次数不得多于当前实现；实测保留量按上面的离线口径确有降低；反复浏览历史的解析 CPU 和提交 p95 的候选对基线差不超过 P0 同场景的 A/A 配对差异。

**暂缓高亮缓存预算调整**：其输出异步到达，淘汰可能引入重新请求和颜色闪变。必须先验证已挂载组件对缓存的依赖，再另行设计，不能直接套用 Markdown 淘汰策略。

### P3：合并相同图片的并发读取

**源码依据**

[client/image-file.ts](../../client/image-file.ts) 的 `useImageFile` 每个实例独立请求；[index.server.ts](../../index.server.ts) 的 `imageRpc` 读取文件并返回完整 base64。当前单图文件大小上限为 3 MiB；显示为缩略图不代表传输的是缩略图。

调用方只有两处：[live-renderers.tsx](../../client/live-renderers.tsx) 第 182 行，仅在工具行展开或预览后请求；[local-image.tsx](../../client/components/markdown/render/local-image.tsx) 第 11 行。同一路径同时在途要求同一张图被多个组件同时请求，目前没有计数证明它发生的频率。

**进入条件**：P0 的图片 RPC 探针在真实场景或回放 fixture 中记录到重复在途请求。没有重复在途请求的证据，本阶段停止，不写代码。

**已核实的身份事实**（只对核实过的版本成立）：

- 宿主 Paseo `759532509`（v0.11.2）的 `packages/app/src/plugins/registry.ts` 第 68 至 105 行按 `serverId/pluginId` 各求值一次客户端 bundle，并把该 server 连接的 `invoke` 绑定给这次安装。因此在这个宿主版本里，插件模块级状态天然按 daemon 连接隔离。
- `@getpaseo/plugin` 0.11.2 的 `dist/client/rpc-context.js` 第 13 至 18 行：`useRpc` 返回的是每个组件实例各自的 `useCallback`，所以 `load` 函数身份不能当去重键；`usePluginRpcContextValue` 没有从 `@getpaseo/plugin/client` 公开导出，插件拿不到 `invoke` 本身。
- `paseo-plugin.json` 声明兼容 `paseo >= 0.8.0`。0.8 到 0.11 之间的宿主是否同样按安装隔离，未核实，不能外推。只核对用户当前使用的版本不能守住这条 manifest 承诺：依赖模块隔离的实现，必须先核实整个声明范围内的宿主都按安装求值，或者宿主 SDK 提供可用的连接身份；两者都没有时不得交付，也不得通过悄悄抬高 manifest 的最低版本来缩小支持范围。

**计划改动**

- 仅共享尚未完成的读取 Promise，不保存长期图片结果。
- 去重键是 `cwd` 与 `path` 的二元组，用无歧义编码（例如 `JSON.stringify([cwd, path])`，或嵌套 Map），不用任意分隔符拼接字符串。键放在模块级 Map 中；连接隔离依赖上面的“每安装一次求值”事实，在代码注释里写明该依赖与核实范围。核实范围必须覆盖 manifest 声明的全部宿主版本范围，见上一节；覆盖不到则停止。
- 请求结束后移除条目；失败后下一次新挂载仍可读取。
- 每个消费者保留独立卸载保护；一个组件卸载不能取消其他消费者需要的结果。
- 文件变更语义写清两种情况：没有同键在途请求时，新挂载保证发起一次新读取；已有同键在途请求时，新挂载共享那一次读取的实际返回结果，不另起读取。文件读取不提供开始时刻的原子快照保证；并发修改文件的结果需要实测，若合并请求会使新挂载显示与既有独立读取语义不一致的内容，则停止 P3。做文件变更用例覆盖两种情况。保留 `useImageFile` 在路径变化时先清空再读取的现有语义。

**预计文件范围**：`client/image-file.ts` 与对应 hook 单测。不扩展公共协议，不引入跨连接的全局路径缓存。

**验收**：同一连接同时请求同图只执行一次，以图片 RPC 探针的重复在途计数归零为主证据；不同工作目录或路径不合并；失败、重试、卸载、重连无串图；缩放、预览、最大化和原图打开行为不变。

服务端缩略图生成、压缩、图片长期缓存不纳入本方案，避免新增依赖、失效策略与画质变化。

### P4：按需初始化高亮语法

**源码依据**

[index.server.ts](../../index.server.ts) 第 268 至 316 行：`buildEngine` 在第一次高亮请求时加载 18 种语法和两套主题，`getEngine` 在失败时丢弃 memo 以便下次重试。第 546 行：包括纯文本提示在内，当前 handler 都先等待 `getEngine()`。

**已核实的 Shiki 4.4.3 依赖事实**（`@shikijs/langs`、`@shikijs/primitive` 的 dist 文件）：

- 硬依赖：`html` 的 `embeddedLangs` 是 `javascript` 和 `css`。`Registry.loadLanguages` 在依赖缺失时抛出 “Missing languages”。按需加载 `html` 必须连带加载这两个。其余 17 种没有硬依赖。
- 懒嵌入：`markdown` 的 `embeddedLangsLazy` 覆盖了支持集合中除 `markdown` 自身、`jsx` 和 `toml` 以外的 15 种：`css`、`html`、`yaml`、`sql`、`diff`、`docker`、`go`、`javascript`、`json`、`powershell`、`python`、`rust`、`shellscript`、`typescript`、`tsx`。`Registry.loadLanguage` 在这 15 种中任一种于 `markdown` 之后加载时，会删除并重建 `markdown` 语法。也就是说，含围栏的 markdown 的高亮结果取决于当时已加载了哪些语法。
- 加载顺序规则：为保持输出等价，`markdown` 必须与上述 15 种作为一组一次性加载，不接受“先少高亮、后补齐”的结果。这意味着任何以 markdown 开头的会话都接近今天的全量加载，按需初始化的收益只剩下不含 markdown 的会话；这是本阶段可能过不了收益检验的主要原因，须在实施前验证中如实报告。
- 别名集合：当前 `resolveLanguage` 依赖 `getLoadedLanguages()` 返回的名字与别名集合。语法文件自带的别名有 `ts`、`cts`、`mts`、`js`、`cjs`、`mjs`、`bash`、`sh`、`shell`、`zsh`、`py`、`yml`、`md`、`rs`、`ps`、`ps1`、`pwsh`。其中 `cts`、`mts`、`cjs`、`mjs`、`ps`、`pwsh` 只靠语法别名工作，不在 `ALIASES` 表内。显式映射必须完整复制这些别名，再加上 `ALIASES` 与 `EXTENSIONS` 两表。
- 并发：`Registry.loadLanguage` 对已解析的语法是幂等的，但动态 import 加注册的过程需要按语言 memo 一个 Promise，失败时丢弃 memo，与现有 `getEngine` 的处理一致；不新增重试或降级分支。
- 缓存影响：客户端与服务端高亮缓存各 200 条，结果保留到被淘汰或模块重建为止。等价性要求本身就排除了“先错后对”的结果进入缓存，因此不以缓存淘汰作为补救手段。

**实施前验证**

1. 单独测量首次请求、后续请求、引擎初始化和 daemon 内存，区分包解析与语法初始化成本。daemon 内存按 P0 的 `process.memoryUsage()` 方法与采样时机执行；引擎初始化另用离线 Node 脚本复测。
2. 分散代价：按需初始化把一次首次高亮延迟拆成每种语言各一次，会话内会出现更多次“先无色后上色”。对 P0 的 fixture 集合，同时报告今天的单次初始化耗时和按需方案下各语言首次加载耗时之和，以及一次会话里首绘无色事件的次数。两者任一明显变差，本阶段停止。
3. 建立所有当前支持语言和 diff 双路高亮的基准输出。

若收益成立，将引擎、主题与语法初始化拆为必要的内部步骤；用显式映射保持当前支持集合与别名，按上面的分组规则加载，合并并发加载同一语言的请求。初始化失败仍遵循既有行为。

**预计文件范围**：`index.server.ts`，必要时新增内部高亮引擎模块，以及 server handler 的等价性测试。目前没有针对 `index.server.ts` 的测试，测试基础设施需要新建；vitest 环境为 node，可直接加载 handler。

**等价性测试（必须）**

- 快照：用今天的急加载引擎导出 `getLoadedLanguages()` 的排序结果作为 fixture；按需实现加载全部语言后必须与之完全相等。
- 解析表：对 `ALIASES`、`EXTENSIONS`、语法别名与语法名的并集中每一个提示和文件名，断言 `resolveLanguage` 的结果与急加载引擎一致。
- 顺序：新引擎先高亮含 ```` ```ts ```` 等围栏的 markdown，再加载 typescript 等语言，输出必须与急加载引擎逐 token 相同。不接受差异。
- 并发：同一语言的并发请求只触发一次加载；加载失败后下一次请求重新尝试。

**验收**：18 种语法、别名、文件名推断、纯文本、未知语言、超限输入、深浅主题和 diff 正文输出等价；并发请求不重复初始化或出现竞态；上面的等价性测试全部通过。

动态 import 在当前单包构建中主要延迟执行，不代表减少下载体积。此阶段不得宣传客户端包或网络加载收益。

## 4. 暂不实施的方向

- 不更换 Markdown 引擎、不扩大自定义 memo 比较器的忽略字段，不降低流式刷新频率。
- 不在插件内另做时间线虚拟化：需先确认宿主边界，避免破坏搜索、选择、滚动定位和展开状态。
- 不直接清理 `timeline-tail` 或 hub 的历史标记：这些状态阻止旧时间线重新覆盖新状态，生命周期优化需独立证明语义安全。
- 不为减包体拆设置页、删除语言、字体或品牌功能。当前设置页与解析器存在体积成本，但尚无真实冷启动瓶颈证据。
- 不调整生产实例、部署插件、推送或改写 Git 历史。

| 阶段 | 确定性证据（计数、单测、等价） | 测量证据（需与 A/A 配对差异比较） | 宿主性能的角色 |
| --- | --- | --- | --- |

性能判定规则：以 P0 测得的当前 A/A 配对差异为唯一阈值来源，候选对基线差与同场景同指标的 A/A 配对差异中绝对值最大的一对比较。内存与延迟属于测量证据，不是确定性证据。以测量为目标指标的阶段（P4，以及 P2 的保留量），收益必须超出对应口径的 A/A 配对差异；以确定性证据为主的阶段（P1、P3，以及 P2 的未命中计数），宿主指标只要求候选对基线差不超过 A/A 配对差异。A/A 差异尚未建立的指标不做判定，只报告。历史基准文档中的噪声数字与本文未测量的收益量级都不得代入。极短耗时同时报告绝对差值，避免百分比夸大。任何可复现的功能、视觉或交互回退直接阻断，不以性能收益抵消。
