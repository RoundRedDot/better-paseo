## 1. 目标与版本边界

下一版本优先缩小 iOS 大 diff、默认工具日志相对不开插件的开销，再确认当前版本是否仍有 Web 历史回放、长会话上翻、布局偏移和资源占用问题。保持现有功能、默认设置和交互契约，每项独立验证、提交和回滚。

- 开发基线：`53ea3ba15faa6fcf685ba0dd90ccb4cabdf8b0f8`，当前已推送、部署的 `main`。
- 已测生产修复：`722238de2fcc1ade46d542a7a540868932d9dc89`；`53ea3ba` 后续只更新文档、证据、截图及离线 showcase，未改变生产代码。
- 最新独立批次：100 core + 60 iOS risk + 60 Web risk，共 220 次；见[已部署修复报告](../bench/2026-10-16-ios-five/parallel/README.md)。
- 历史三方全矩阵：Better Paseo `48a6646`，见[330 次报告](../bench/2026-10-16-readme/README.md)。
- 新夹具长历史：Better Paseo `c4c9f3f`，80 次，见[完整结果](../bench/2026-10-16-history-complete/RESULTS.md)。
- Beautiful Chat 对照固定 `42b61d8`，不开插件对照使用同一宿主、构建及输入。旧数字只提供线索，不拼接成最新版本的三方结果。

本计划承接[上一轮计划](2026-10-15-performance-optimization-next.md)，但以最新证据修正优先级。旧 `tool-expanded-streaming` 夹具没有展开操作，统一称“默认工具日志”；`history-100` 只作为夹具标识，不称为 100 个实际 provider turn。

## 3. 实施顺序与诊断门槛

### 阶段 A：冻结基线，建立反馈循环

1. 从开发基线新建独立 worktree；记录候选起点、宿主 SHA、依赖锁文件、构建产物、探针、夹具和 runner 的哈希。禁止混入保留 worktree `perf-m0-o1` 的未提交代码与测试；需要复用时先单独审阅、证明行为等价。
2. 在 Mac Studio 仅用私有 home、daemon、Metro、缓存和测试模拟器。先执行功能 smoke，再启动诊断计时；准备、编译、失败 smoke 单列。
3. 用五个原 core 场景跑 native/current-a/current-b，各 5 次，共 75 个诊断样本；模式轮换，同 fixture/rep 保持相同环境。current-a/b 必须为完全相同的代码、设置和构建。
4. 默认先申请单计时 lane 的低并发确认窗口，其他初始化不得重叠。若执行时采用用户授权的并行方案，必须从该批开始固定并发协议并分层报告；不得混合两种条件计算版本提升。
5. 保存全部成功、失败和波动样本。不得挑选重跑替换成功数据；噪声过大时新建独立批次，旧批次保持原样。
6. 每项生产修改前，先形成一条已经运行过、能够捕获该缺陷的命令，以及真实调用路径上的失败测试或性能反馈。尚无反馈循环时，只补测量，不实施猜测性优化。

资源准入沿用已验证门槛：CPU idle ≥15%、memory-pressure free ≥10%、pressure level 1；load 只记录。起止均记录资源、真实 runner PID、serverId、UDID、端口和任务区间；进程匹配支持绝对 Node 路径，空进程数组不得解释为零并发。

### 阶段 B：I1/I2，分别定位、分别修复

已知证据：singleton 重复发布及 reasoning 子树重复渲染已在 `722238d` 修复。大 diff 仍集中于工具行；默认日志的提交数已接近 native，但工具行累计耗时仍偏高。这些是归因线索，不是剩余根因的证明。

先复现并最小化，再按实测成本排序提出 3–5 个可证伪假设，每次仅验证一个变量。初始探针范围如下，不预先承诺对应生产改动：

| 范围 | 要回答的问题 | 必须记录的信号 |
| --- | --- | --- |
| 工具映射与摘要 | 折叠状态是否反复处理当前无需展示的大段输出或 diff？ | renderer、分类、摘要调用次数；输入长度；各阶段耗时 |
| 工具行与 disclosure | 重复更新来自哪些 props、订阅或布局回调？ | mount/render/commit 数量、变化字段、header/body 子树成本 |
| 关闭的工具正文及预览 | 折叠时是否仍创建或解析不可见内容？ | 实际正文挂载数、解析次数、预览准备次数、完整复制来源 |
| diff 路径 | 成本发生在折叠摘要、展开准备、diff 解析还是布局？ | 实际展开状态、解析输入与次数、宽度测量及布局事件 |

归因成立后才选择最小修复，例如复用未变结果、消除重复计算或收紧订阅更新。缓存必须有明确生命周期和失效条件；不引入无界缓存、不吞掉更新、不增加 fallback 路径。不能通过删除功能或改变默认展开状态取得“改善”。

每个候选先通过失败回归测试，再比较 current/candidate 同轮 A/A。若功能代价高于收益、收益落入噪声范围或因果归因不成立，停止该候选并保留诊断结论。

### 阶段 C：W1/H1/H2，当前版本复测后再决定修改

- Web 先复测 `history-100` 与默认工具日志，分开报告 Task、Script、行渲染、提交数和 DOM。只有当前版本仍复现时，才检查信息栏、历史订阅、工具行等实际热点；不直接套用旧 O1 补丁。
- 长历史保留 `history-complete-v1` 的 810 条／1 turn 和 832 条／12 turns、59,427 字符尾部回复及默认设置，测冷打开、第一次真实上翻、离开会话后整体返回三阶段。
- 上翻记录前后游标、实际 provider turn、可见范围、各类行的数量、挂载集合与提交集合。先说明工作量差异，再判断相对 Beautiful Chat 的行渲染比例是否有意义。
- 在同一输入上另建用户可见就绪信号；JS-ready、timer gap、rAF gap、累计行渲染分别报告，不互相替代。计时边界与“可用视口”断言须先写入协议。
- 原重复 key 输入单独作为功能回归。新夹具成功不代表旧输入已修复；修复若需要宿主改动，应单独提出上游方案，不修改日常宿主规避问题。

### 阶段 D：V1/R1/R2，仅处理可证明的冗余

- 用 layout-shift entries 定位发生偏移的节点、时刻和交互，结合滚动锚点验证；思考场景小基数采用绝对 CLS 差值，不用巨大百分比描述影响。
- 相同强制 GC 条件下测空会话、完整回放后、离开会话后、重新进入后 JS 堆；至少 5 次，保留原始值和保留路径。堆快照采集单列，不与正式速度计时重叠。
- DOM 按功能归类，检查不可见正文、重复 wrapper、离开会话后仍存活的节点。只能减少冗余，保留表格选区、复制、预览、查找、图片及无障碍结构。
- 不自动重开旧 P2 Markdown 缓存预算、P4 高亮初始化方案；须有当前版本的新证据推翻既有止损结论。

### 功能回归

- singleton 工具行读取当前值；多面板、分组合并、顺序、完成和历史回放正确。
- reasoning 保留完整 host reveal 输入；流式中途展开首帧有当前正文，标题、全文复制和完成后展开状态正确。

- 默认日志流式期间保持默认折叠；展开、长按预览、滚动锚点及当前完整内容复制正确。真正展开体性能另设具备实际展开操作的夹具，不复用旧名称作证明。

## 6. 判定标准与止损

1. **稳定性先行。** 每个场景分别给出两组 A/A 的 5 对值、最大配对差、中位数及 min–max。A/A 超过 10% 的场景不能仅凭中位数称为稳定提升；另立低并发确认批次，不放宽阈值凑通过。
2. **P0 目标。** 在有效且稳定的同轮比较中，I1/I2 的 candidate `allRows.sum` 不超过 native 的 1.10 倍；相对 current 的改善还须超出对应同轮 A/A 波动。未达到则如实保留未闭合状态。
3. **其他速度指标。** 行渲染按 10% 比较；Web Task 保留双方均小于 0.5 秒的持平规则。W1 若当前版本已不复现，转为回归项；若仍复现，目标进入 native ±10%，不得只证明比旧插件快。
4. **Beautiful Chat 对照。** 可比场景不新增超过 10% 的时间开销；H1 先证明行集合和计时边界可比。无法对齐时只报告不同工作量，不声称已达到三方持平。
5. **CLS／资源。** CLS 看绝对增量、触发源和 A/A；堆使用 MB 差值，DOM 使用节点差值，均不套用 Task 的 0.5 秒规则。先测量并登记当前版本的噪声及目标，再修改；不得把删掉功能所减少的资源算收益。
6. **功能和证据。** 零新增功能／显示错误；正式样本齐全、无静默排除，源码与执行工具可追溯；不以单次 commit p95、timer gap 或分项中位数相加替代总体成本。
7. **真实设备。** 模拟器通过仅关闭模拟器验收项。iPhone 15 Pro 的 iOS、Paseo 客户端版本和构建方式需记录后单独验证；当前未知版本不得猜测，未完成时不标为真机 Release 已通过。

## 7. 交付与回滚

- 每项交付包含复现命令、已证实根因、最小 patch、修复前后的功能测试、独立性能证据、未闭合项及回滚 SHA。证据目录保留失败、噪声、环境变化和清理记录。
- 先收敛 I1/I2，再决定是否把 W1/H1/H2 或 V1/R1/R2 纳入同一版本；无法定位的项止损并写明，不扩大生产修改范围追赶数字。
- 最终 README 同时展示 native、Beautiful Chat、当前基线、候选版，明确构建和采样制度；只发布审计通过且具有对应版本证据的数据。保留现有浅深色截图机制。
- 每个独立修改使用英文 Conventional Commits，遵循仓库作者和共同作者规则。提交、推送、合并、部署由后续明确授权控制，不因文档创建自动执行。
- 部署若获授权，使用精确提交 SHA，读回 `enabled/running`、安装版本和关键文件字节；回滚恢复该次部署前记录的精确 SHA，不重启整个 daemon。
- 测试结束只关闭本任务拥有的进程和端口，按父子 PID 关系校验；保留日常 daemon、Align205 和受保护 AVD。worktree 清理前保存未提交材料并验证归档。
